Context

See the proposal for motivation. Telescope 0.2.1 provides a static shell, CommonMark content, gallery planning, route-local islands and a reusable native host. Its extension contract accepts one page route per page adapter and separate island registrations. There is no tutorial catalog, lesson model, execution scheduler or case-checking contract.

Smithy's tour separates model, source loading, lesson state/view, browser effects and native checks, but those packages import Smithy playground types. The reusable behavior is already visible; copying the packages intact would also copy Smithy output enums, severities, filenames and worker messages. The codec workspace extends value lessons with serialization profiles, which makes a shared fixed list of engine modes especially unsuitable.

The accepted domain ownership contract still applies. This change proposes generic tutorial behavior, not a move of Smithy's playground engine into Telescope. Repository inputs and consumer JavaScript remain reviewed content. This design adds no runtime package discovery.

Goals and non-goals

Provide independently usable content planning, a general code editor, tutorial workspace state/views and case comparison packages. The code editor owns formatting and is usable on any consumer page without tutorial configuration or execution engines. The standard host composes it with tutorial behavior to build a course. A static course must require no execution provider. An unrelated consumer must prove both standalone editing and tutorial composition before Smithy adoption.

Keep Smithy's lesson corpus, model validation, converters, JSON-RPC semantics, codec profiles, Java reference tooling, Morphir fixtures and playground encoding in Smithy. This change does not create a general learning-management system, user accounts, progress scoring, remote execution, collaboration or a whole-site client router. It does not migrate Smithy or diagrams.mbt, or publish a release without owner approval.

Use a small composition helper to produce a tutorial site plan, rather than require consumers to register each lesson as a custom page. The existing site renderer merges this plan before collision checks, search creation and shell rendering. The shared host remains the sole owner of filesystem promotion. Components have stable public contracts but remain in the single moonrockz/telescope distribution.

The dependency direction is tutorial/* to editor, editor/views and editor/browser. General editor packages never import tutorial packages. The editor API accepts document identities, text, declared languages, optional context documents, provider bindings and change listeners. It requires no course, lesson, persistence key or evaluator. A standalone page mounts it directly or through an existing route-local island registration. Tutorial code translates its manifest data into the same editor configuration.

Alternative: one copied tour executable would be quicker for Smithy but would retain its imports and prevent reuse. A separate published package for every control would add release coordination without a demonstrated need.

SRC-1. An explicit catalog, independent of folder numbering

Add an optional tutorials path in site JSON referencing site/tutorials.toml. The tutorial manifest itself uses TOML. Parse it separately from the existing public SiteConfig record, and pass an optional tutorial plan into rendering. Do not add required fields to existing public configuration, Registry or view records. Add defaulted host arguments for compiled tutorial providers. Existing call sites and site JSON configuration remain valid.

The TOML manifest has schema_version = 1, an input root, registered browser providers and an ordered list of courses. Each course has an ID, title, configured route prefix and ordered lessons. Each lesson has a stable slug, title, section, Markdown path and optional reference links. Interactive entries declare files, provider ID, operation, options and cases. Optional formatter registrations declare supported languages, provider version and worker assets. The formatting.languages table supplies language defaults, and a file's explicit formatter binding overrides its language default. Both bindings contain a provider ID and options table. These tables adapt the general editor's registration contract for tutorial authoring; a standalone editor receives equivalent bindings directly without this manifest. Absence of either leaves formatting unavailable. All structural keys are strict; only provider-owned options tables are open. Static entries reject execution-only fields. Virtual filenames permit normalized subdirectories for comparison inputs, but never absolute paths, traversal, duplicate names or backslashes.

# site/tutorials.toml
schema_version = 1
root = "site/learning"

[formatting.languages.text]
provider = "sample.whitespace"
options = {}

[[formatters]]
id = "sample.whitespace"
contract_version = 1
formatter_version = "1.0.0"
languages = ["text"]
worker = "assets/whitespace-worker.js"
assets = ["assets/whitespace-worker.js"]

[[providers]]
id = "sample.text"
contract_version = 1
engine_version = "1.0.0"
operations = ["evaluate"]
worker = "assets/text-worker.js"
assets = ["assets/text-worker.js"]

[[courses]]
id = "getting-started"
title = "Getting started"
route = "/learn/"

[[courses.lessons]]
slug = "first-check"
title = "First check"
section = "Basics"
prose = "first/lesson.md"
files = [{ name = "input.txt", source = "first/input.txt", language = "text" }]
execution = { provider = "sample.text", operation = "evaluate", options = {} }
cases = [{ id = "start", expect = "first/cases/start.json" }]

TOML is the authored manifest format. Its comments and tables make provider configuration and nested courses easier to maintain. Use the pinned moonbit-community/toml@0.5.0 parser behind a portable decoding boundary and qualify it with the repository's pinned compiler in the first slice. Read files only through the existing async host. Preserve parser line/column information in syntax diagnostics and report semantic field paths for schema errors. Reject duplicate keys and invalid field types; do not silently accept a JSON tutorial manifest or auto-convert source files.

Decode TOML into format-independent typed tutorial data. Normalize options to JSON-compatible strings, booleans, finite numbers, arrays and string-keyed tables; absent optional fields represent omission. Reject date/time and non-finite numeric values with a field diagnostic rather than silently stringify them. Canonicalize table keys for revision calculation and serialization while preserving course/lesson/file array order. Manifest comments, whitespace and table-key order must not alter saved-edit revisions or generated site bytes. Runtime envelopes, generated data, machine-readable reports and the case expectation fixtures retain their JSON representations.

This is the proposed wire shape to implement and document, not accepted configuration in 0.2.1. Provider asset paths are relative to the declared input root and copied under a reserved per-provider output directory. A course at /learn/ places its lesson at /learn/first-check/. A second course chooses a different prefix. Stable routes use slugs, while position and previous/next come from array order. Register the prose source-to-route mapping before link rewriting, so authored repository links work. Case expectations and overlay files never enter public content discovery or search.

Alternatives: an authored JSON manifest lacks comments and makes nested course configuration harder to scan; supporting both encodings adds a compatibility obligation before the tutorial format has shipped. Preserve one TOML authoring contract and a format-independent model. Mandatory NN-slug directories and the smithy.io-only reference check would expose Smithy's conventions as common constraints. Smithy can translate its layout through a consumer adapter in a later adoption change.

API-1. Separate tutorial contracts, with explicit browser and native roles

Keep extension Registry version 1 unchanged. Introduce a tutorial execution registry/protocol and a separate general editor registry/formatting protocol, each beginning at contract version 1. Execution registrations declare engine identity, operations, worker assets and optional workbench handoff. General editor registrations declare editing/language adapters and formatters independently of execution providers. The tutorial composition validates and passes through these editor registrations without owning their types. Standalone editors use the same registry with no tutorial registration. All imports, worker chunks and WASM companions must be listed as contained assets. Unknown providers, duplicate IDs, unsupported formatter languages and unsupported operations fail the build. No config string selects a native package to load.

The stock CLI reads declarative registrations, validates their structure and copies prebuilt assets. It never compiles or executes the consumer engine during rendering. A consumer driver imports the public host and passes compiled evaluators and include/reference policies through defaulted tutorial-specific arguments. A compiled evaluator must match the declarative provider identity, engine version and capabilities. The case-check entry point requires an evaluator for every executable lesson selected; missing evaluators fail explicitly. A plain built-site link check retains its existing meaning and cannot stand in for case execution.

Consumer adapters map model validation, output conversion, value checks, message checks, comparison and transcripts to these results. Severity-to-blocking rules belong there. Preserve provider metadata in check reports and the build record without treating it as proof that execution succeeded.

Alternative: extend Smithy's closed Engine and Answer enums in Telescope. Every new domain operation would then require a shared release. An unstructured HTML callback alone would avoid types but lose reusable diagnostics, scheduling and expectations.

RUN-1. Share the scheduler and make stale results unobservable

Adapt Smithy's update/effect loop into a pure workspace package. Keep one worker per mounted workspace and at most one active request. Debounce edits for 250 ms by default and coalesce pending revisions. Identify both worker generation and request revision, so late replies, queued timers and reset races cannot replace current results. Clear or mark previous results as pending after edits. Persist files separately from execution state.

Use a 10-second default request deadline and at most one automatic retry for an unchanged revision. Restart the worker before retrying. A second timeout ends automatic work until a new edit or explicit retry. Decode failures and incompatible protocol versions show a failure immediately without repeated automatic restarts. Navigating away disposes workers, editors and timers. Execution stays on the reader's device; no network execution backend is provided.

For stepping, remember the reader's requested position independently from the runtime session. An edit or restart starts a new session and replays up to that position or the new end. Reset restores starting files and new editor histories while preserving pane layout. Runtime assertions for cases always use a fresh independent session.

Saved edits use a namespaced key containing site identity, effective deployment base/version, course ID and lesson slug. Accept them only when file identities and the starting-input revision match. Compute the revision deterministically from the tutorial schema, ordered starting file names/text, operation, options and provider identity/version. This fingerprint is only for freshness, never an artifact-integrity promise or a revival of gallery digests. Denied or corrupt storage falls back to current in-memory files.

Alternative: let every engine own request timers, persistence and stale-reply handling. That would reproduce the most failure-prone tour logic in each consumer.

UI-1. Render reading first, enhance the workspace on its own route

Render the course contents, lesson prose, references, source links, starting-file text/downloads and previous/next links in the static shell. Index prose and expanded includes through the existing content facts. Add tutorial navigation through optional view inputs without changing the meaning of existing page sections. Static lessons use the documentation reading width and include controls only. Interactive lessons reserve a workspace mount alongside readable prose. Hide inactive execution controls until enhancement succeeds.

The general editor/browser package provides a default plain-text adapter and a separately bundled CodeMirror adapter for rich editing. Pin selected dependencies and their license records during implementation. Extract generic editor mechanics from Smithy's CodeMirror bridge; do not ship its Smithy language module or globalThis.smithyEditors name. Consumers add their own language extensions. Rich editor and formatter assets load only on pages explicitly embedding those components, including standalone documentation/playground pages and interactive lessons. Small read-only code-group controls may load on static lessons without loading any editor or worker.

Use labeled selectors with correct keyboard behavior, literal text rendering, polite status messages, accessible pane expansion and responsive stacked panes. Preserve editors while panes are hidden and remeasure on reveal. Theme tokens follow Telescope's accepted palette. Output changes are calculated per output ID; no prior successful output means no change highlight. A provider's unknown presentation kind falls back to labeled text rather than fabricated domain UI.

Alternative: mount a full client application on every page or require scripts to read examples. Both conflict with Telescope's static reading and route-local asset requirements.

HIL-1. Ship MoonBit highlighting in the general rich editor

Include a standard MoonBit language adapter with the rich editor/browser distribution. Both declared language IDs moonbit and mbt select it without custom consumer registration. Standalone editors and tutorials use the same adapter. Keep the existing language-extension mechanism for additional languages and explicit replacement adapters. No filename inference or formatter registration is required to select the mode.

Implement a CodeMirror stream-language adapter using its existing language/highlight dependencies. Smithy's static MoonBit scanner and token tests supply a pinned source reference, while its Smithy stream adapter supplies the browser integration pattern. Extend the MoonBit mode for the pinned toolchain's keywords, numeric/string/character literals, escaped strings, line and documentation comments, annotations and #| multiline string lines. Use representative Telescope source fixtures for declarations, traits, pattern matching and package-qualified references. This is lexical highlighting, with no compiler or semantic engine dependency.

Reconfigure language compartments per document and use incremental highlighting during edits, including incomplete source. Reuse the editor theme tokens for light and dark styling. Changing highlighting or language must not replace text, reset selections/histories or emit an edit event. The plain-text adapter and unknown modes keep readable source. MoonBit mode assets load with the configured rich editor where needed; unrelated pages and static lessons do not acquire its dependencies.

Verify token classes with focused fixtures for both aliases, escaped and multiline strings, documentation comments, annotations and incomplete-then-completed source. Chromium coverage must inspect actual syntax styling and live updates on a standalone editor with no tutorial configuration or engine, then on the same component inside a tutorial. Exercise document/language switching, exact text preservation, selection, Undo, formatting coexistence and both themes. Additions to this editor mode do not claim compiler diagnostics or MoonBit formatting support.

Alternatives: require consumers to supply MoonBit support, or reuse static HTML token markup inside an editable document. The first omits a required standard editor capability; the second does not provide the editor's incremental language integration.

FMT-1. The general code editor owns its open formatter trait

Expose an externally implementable Formatter trait from moonrockz/telescope/editor. Its portable contract has no CodeMirror, DOM, tutorial or execution-engine dependency. It applies wherever the code editor is used. The proposed trait shape is:

pub(open) trait Formatter {
  fn format(Self, FormatInput) -> Result[FormatOutput, FormatError]
}

FormatInput contains a target editor document with stable identity, virtual filename, text and declared language, optional immutable context documents, and consumer options. All document/request/result/error types belong to editor. A standalone single-document editor supplies no additional context. A tutorial caller supplies other relevant files through the same general API. FormatOutput contains the target document's complete formatted text. FormatError carries a displayable code and message. The formatter computes text only and cannot mutate editor state or other documents through this contract.

The general editor registry declares formatter ID, contract version, formatter version, supported languages and prebuilt browser worker assets. Language defaults and per-document overrides select a provider explicitly. There is no extension-based discovery. Both plain and rich adapters expose the same optional keyboard-accessible Format action. A small original whitespace formatter in the independent consumer proves the same implementation on a standalone editor page and in a tutorial. The standalone fixture imports no tutorial packages and supplies no manifest, course, lesson or evaluator.

A consumer compiles its trait implementation into a formatter worker using the shared editor/browser bridge. The host validates and copies its declared assets without invoking formatting during build. Worker transport echoes editor instance, formatter identity/version, generation, request ID, target identity and revisions for all captured input documents. The trait stays synchronous and portable; the bridge invokes it off the UI thread and returns asynchronously. Its worker can be terminated after the 10-second default deadline independently of any caller's other processing. Keep at most one active formatting request per editor instance and make retries explicit.

The editor applies changed text only when instance identity, formatter, target identity and all captured input revisions still match. Switching tabs alone does not invalidate a request; a valid reply updates its originating document without changing selection or focus in another document. Input edits, reset/replacement, formatter replacement and disposal invalidate older results. Apply changed text as one undoable transaction, retain that document's history and map its selection into the new text. Emit the normal document-change event. An unchanged result adds neither history nor an event. Errors, malformed replies and timeouts preserve text, selection and history and announce a failure without moving focus.

Persistence, execution and course state belong to the caller. The editor never starts lesson checks or derives lesson storage keys. Tutorial composition listens to its normal changes to save edits, invalidate results, recheck and replay step sessions; standalone callers choose their own behavior. Tutorial Reset calls the editor's document reset API to invalidate pending formatting. Formatting is an explicit document action, never a build side effect or an automatic rewrite of fixtures, expectations or outputs. Content remains on the reader's device.

Alternatives: place Formatter in a tutorial package, use a CodeMirror-only callback, or require every execution engine to implement formatting. Each couples the code editor's general formatting behavior to another feature. The shared editor contract supports reuse without any tutorial dependency.

CHK-1. Separate case execution, reference evidence and rendering

The portable comparator accepts normalized results and expectations. Native host orchestration applies named overlays, creates a fresh evaluation/session, compares complete diagnostic keys with multiplicity, checks nonempty output needles, blocked reasons, verdicts and step positions, and emits text/JSON reports. Sort courses by manifest order, cases by ID and diagnostics by key for reproducible reporting. Report source, course, lesson, case, provider/version and input revision. Never regenerate expectations to fit a result.

Source includes use an explicit include fence with labeled path#region entries. Support neutral tutorial:start/tutorial:end markers; an explicit consumer policy can map Smithy's existing tour:start/tour:end markers. Track fences while extracting so marker-like code is not interpreted as a boundary. Preserve each included code block's language and source reference. Reject unclosed or repeated markers, nested malformed regions, missing files and regions with no approved tested block.

A consumer policy supplies the allowed test sources, fence forms, runner identity and optional evidence report. Structural inclusion proves only that the region is covered by that declared policy. A verification claim requires a successful runner report for the same source bytes and relevant provider inputs. Builds never execute shell fences. Optional consumer guards detect hand-written domain CLI/API examples outside approved regions. Telescope does not hard-code Smithy commands, MoonBit aliases or a particular README path.

Reference comparisons are an optional compiled hook over case results and supplied evidence. The hook owns domain comparison and tracked differences. Reports retain its pinned reference source, input revision and explicit difference reasons/tracking references. Required stale evidence fails checking. Smithy's Java reference generator, vendored traits, Morphir inventory and stale allow-list tests stay in Smithy. No Java runtime is required by Telescope.

Expose case checking as a reusable host API and a small consumer-driver command, documented separately from telescope check, which continues to inspect built output. The stock CLI can structurally build a tutorial with browser assets, but cannot claim executable cases passed without an evaluator/report. This makes build-only use practical and its limits visible.

Alternative: run arbitrary commands from lesson metadata during build. That mixes rendering with execution and obscures which runner supports the teaching claim. Always requiring Java would make unrelated tutorials depend on Smithy's reference setup.

REL-1. Prove reuse before adapting a consumer

The first implementation group delivers a minimal static lesson and one editable plain-text lesson through the packaged library and CLI in a new temporary consumer, with its own small evaluator/worker. No Smithy import, absolute developer path or sibling workspace is allowed. A candidate-only explicit registry/cache is permitted for qualification, as in the existing consumer test. It is not a usable downstream dependency or publication evidence.

Later groups extend that same neutral fixture with rich editing, a standalone non-tutorial editor using the consumer's Formatter implementation, tutorial composition using that same formatter, comparison, steps and tested includes. Smithy's source inventory and parity matrix guide the acceptance cases, without copying its engine into Telescope. Publication is an owner gate for one real matching library/CLI version. A separate Smithy change can then translate its existing content format and wrap its actual engine. Do not record that migration as completed here.

Alternative: migrate Smithy first through local path dependencies. That would hide packaging and ownership defects and violate the released dependency contract.

Verification approach

Map each scenario in code-editor, site-tutorials, site-tutorial-workspaces, site-tutorial-checks and the extension delta to a focused automated check. Portable tests cover catalog rules, overlays, comparison, general editor/formatter bindings and scheduling. Language-adapter fixtures cover MoonBit tokenization and exact source preservation. Native host tests cover containment, symlinks, asset collisions, staged failure, diagnostics and deterministic builds. An independent standalone consumer imports only the editor APIs and implements Formatter. Browser tests cover multiple editor instances, both adapters, live MoonBit highlighting, language switches, formatting/Undo, failed/stale replies, tutorial integration, execution workers, keyboard behavior, no-script reading and 360-pixel layouts in both themes.

Keep engine tests separate from fixture qualification. Run mise run check for strict engine checks and mise run test:browser for Chromium behavior after relevant implementation groups. Build and package before mise run test:consumer -- --prepared. The fresh consumer must use the packaged public host, expose its own evaluator and render under both a root and nested/versioned base. Existing gallery and version-one extension fixtures remain regression coverage. Group-specific tests and authoring/contract documentation land with each group.

Before review run mise run format, mise run check:setup and mise exec -- openspec validate --all --strict. Planning validates these artifacts and local HTML references; it does not prove new runtime behavior or run tests against unchanged Smithy workspaces.

Migration plan

  1. After maintainer approval, create a Telescope-local epic and one story for each numbered group in tasks.md. Claim each before implementation and record dependencies.
  2. Implement the independent consumer path first, then catalog, editing, optional execution modes and checks. Keep each slice's tests and documentation in that slice. Adapt only generic source from the pinned inventory with attribution.
  3. Qualify the candidate library and matching CLI on supported native platforms and Chromium. Record versions, checksums, supported targets and the separation between rendering and case execution.
  4. Prepare a release PR. Publication remains blocked until the owner approves the exact commit/version through the existing release procedure. Do not choose or advertise a speculative dependency version during planning.
  5. After real publication, qualify a clean consumer against the actual registry and CLI archive without candidate caches or local overrides. Archive this change in the final verification/documentation PR, merge its deltas and repair asset paths and inbound links.
  6. Close stories only after their PRs merge with the PR and merge SHA; close the epic after all stories merge. A later Smithy-owned proposal handles content translation, adapter integration and any edit-storage migration.

Rollback is additive. Existing consumers can keep 0.2.1 or remove the opt-in tutorial manifest reference. A failed staged build never replaces the previous site. Once adopted, a consumer rolls back the matching library/CLI and its own adapter together; no server-side tutorial state requires migration.
