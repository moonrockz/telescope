Goals and boundaries

The first release must build an unrelated project's small site and expose enough optional API/version support for diagrams to migrate without URL regressions. Keep configuration, paths and document facts independent from host IO and consumer domain dependencies. A shared source snapshot is evidence for extraction, not an instruction to copy every feature.

Exclude diagram parsing, rendering, animations, domain editors and workbenches, hosting and deployment, remote plugin discovery, arbitrary runtime plugins, and wholesale Smithy/Morphir migrations. The initial preview serves an existing build. Automatic watch/rebuild is deferred unless independently scoped later.

Architecture decisions

PKG-1. One library and one CLI

Publish one module moonrockz/telescope with independently importable packages and a matching native telescope CLI. The library supports custom Rabbita pages and exposes native IO through moonrockz/telescope/host, including compile-time providers. The CLI is a thin stock consumer of that same host. A CLI-only design would force custom pages through opaque configuration. A library-only design would make every consumer rebuild the host orchestration. A generic plugin platform would introduce discovery, ABI and trust policy before there is evidence for it. Start with explicit, compile-time adapters and versioned data contracts.

contentPure front matter, heading/link analysis and content planning over supplied textmodel; no filesystem, process, browser or consumer engine

The proposed source layout is pkgs/telescope/ for the published module and apps/telescope/ for the CLI, with internal workspace membership only inside Telescope. Consumers resolve real versions from the package registry. Package imports keep core usable without loading optional adapters or browser assets. A dependency check must reject imports of Smithy, Morphir or diagrams engines from Telescope packages.

CORE-1. Pure content planning, effectful host

Pass file text and source metadata into pure analysis, then produce a route/output plan. CommonMark rendering currently uses a native backend in the inspected sites, so it belongs behind a host renderer adapter; do not promise that this backend runs on every target. Core contracts remain pure and testable across targets. The host reads files with moonbitlang/async, invokes the renderer, resolves providers, asks the shell for HTML, validates the full plan, then writes a staged output tree. Promote only a completed build. Repeated declared inputs produce the same output files and bytes.

Pin implementation dependencies when added. The observed candidate baseline is Rabbita 0.16.5, cmark 0.4.12, async 0.22.5 and x 0.5.5 from diagrams, with Smithy using Rabbita 0.16.4 and Morphir 0.16.3. Group 1 must qualify the chosen pins together. Setup already pins Node, OpenSpec and MoonBit separately; no engine module or dependency claim exists yet.

HTML-1. Reviewed HTML remains a first-class input

Markdown and HTML fragments use the Rabbita shell; complete HTML documents keep their own head and body. Preserve explicit IDs, resource paths and reviewed raw HTML, then derive navigation/search facts. This supports existing design documents. The input trust model is reviewed repository content, as in the sources. A future untrusted upload service needs a separate sanitizer policy. Resolve URLs and resources after route assignment, including embedded local CSS/JS. Detect duplicate routes and heading IDs rather than silently overwriting them.

Source discovery is explicit and deterministically sorted. Exclude docs/templates/, .agents/, openspec/, docs/superpowers/, build output and dependencies by default. Public inclusion is opt-in. Keeping Telescope's development assets in docs/templates/ is safe only with this exclusion; diagrams currently stores its planning template under .agents/templates/ to avoid changing its engine during planning.

Consumers can declare static directory mappings through static: [{from, to}] in host configuration. Both directories use normalized relative paths; inputs stay within the project and their declared root, and output paths participate in collision checks. This preserves existing asset URLs without coupling general resources to a page or fence callback. Copies retain supplied bytes and configured development exclusions.

EXT-1. Typed adapters with declared inputs

Expose a versioned adapter record with unique ID, contract version, supported fence labels or route, and a render callback returning body HTML, text/heading facts, diagnostics and declared assets. The consumer compiles adapters into a small native driver using the library; the stock CLI consumes standard configuration and prebuilt artifact manifests. It never discovers or executes arbitrary packages from configuration. An unsupported fence remains escaped source code. A custom island adds a mount ID, script and optional stylesheet only to its registered routes. Fence inputs include a one-based ordinal within their adapter in the document, so repeated diagrams can use distinct SVG prefixes without mutable callback state.

All host reads go through the explicit artifact/input boundary. Provider failures carry provider ID, source and stage. User-provided raw HTML has the same reviewed-source trust model as HTML content. This typed extension choice avoids premature runtime loading while leaving consumers free to compile their own domains without a Telescope fork. The stable contract is adapter version 1; binary ABI compatibility is not promised.

API-1. Optional API ingestion is in the usable first release

Generalize the observed moon doc reader as an optional adapter. Accept module and package metadata plus README content and an explicit source ref. Preserve package/index ordering, item and method anchors, docstring Markdown, api: links, qualified type/trait links, source file/line links, missing-prose warnings and API search facts. Unsupported metadata shapes fail with a diagnostic. Test against the recorded notebooks fixture and freshly generated data from the pinned compiler. The consumer chooses modules and invokes moon doc; Telescope must not import those modules' engines.

VER-1. Generic tree assembly, consumer release policy

Provide a deterministic adapter over already checked output trees and a consumer-supplied version manifest. Preserve root, next/, v/<minor>/, latest/, tree-local search, static banners and same-page selection with the current fallback behavior. Reserve next, v and latest prefixes. The consumer retains release eligibility, tag listing, download/checksum policy and deploy. Copying diagrams' gh release lookups into the core would couple a static toolkit to one host and release strategy.

DIST-1. Package proof before publication, publication before adoption

Group 1 builds a thin library and CLI candidate, packages them, and tests a fresh consumer outside all source workspaces. A temporary isolated registry/cache seeded with that package is permitted only as a prerelease qualification input, with a recorded package version and source. The consumer manifest must contain a versioned registry dependency, no local path or sibling module. This test proves distribution shape early without requiring unauthorized publication.

The usable release adds the scoped contracts below, then the owner approves publication through a release PR. Target native CLI archives for Linux x64 and macOS arm64 first. Publish through owner-approved GitHub Actions the library and matching CLI version with license notices and SHA-256 checksums, then repeat the fresh-consumer test from the real registry and release downloads. If either artifact is unavailable, adoption remains blocked. No invented future version is written into diagrams. Other operating systems or architectures remain unqualified until their installer and consumer tests pass.

Consumer and gallery contracts

Proposed CLI commands are telescope build --config site/site.json --out _site, telescope check --config site/site.json --out _site --format text|json, telescope serve --config site/site.json --out _site --port 4173 and telescope assemble --manifest site/versions.json --out _site. Build and serve accept an explicit base-path override for preview. --version reports the installed release. Configuration and manifest contracts use schema_version: 1; unsupported versions fail before writing.

Configuration contains consumer title, description, repository URL/ref, canonical site URL, base path, public source roots, navigation groups, package/chapter ordering and optional API, versions, gallery and island inputs. Preserve existing diagrams semantics through its thin config adapter rather than forcing hardcoded pkgs/ layout into every project. Engine/source lookup paths stay consumer-relative. The CLI refuses overlapping input/output roots and path escapes.

The gallery is a presentation contract over files already generated and checked by the consumer. Each entry has a stable unique ID, family, title and explicit implemented or planned status. Implemented entries require source records and an SVG preview; an offline HTML player is optional. Every file record includes a relative path and media type. Planned entries contain descriptive metadata and no fabricated runnable artifact. An optional informational producer record can identify the consumer pipeline. It is not a freshness check and is not required to build the gallery.

Normalize relative paths, reject absolute paths and traversal, resolve symlinks against the declared root, require regular files before staging. Preserve supplied file bytes and directory relationships needed by offline players, including any declared companion assets. Reject missing or undeclared companions. Check output collisions and keep output writes inside the destination root.

Delivery and migration sequence

  1. Approve this proposal, then create the repository-local epic and per-group stories.
  2. Prove independent packaged consumption in group 1, before expanding content features.
  3. Implement content, shell, host, extension/gallery and API/version contracts with tests and docs in their own groups.
  4. Prepare release artifacts and install instructions. The owner explicitly approves the release PR; GitHub Actions publishes and maintainers verify library and CLI distribution at the same actual version. The final verification/documentation PR records published-install evidence and archives the change; the release group stays open until it merges.
  5. Report release coordinates and clean-consumer evidence to mailbox run:run_b3638d9bfa3d. Only then may diagrams' adopt-telescope-site pin that version and migrate.
  6. Archive this completed change in its last implementation PR, repair asset and inbound links, merge, then close stories and a finished epic with PR and merge SHA.

Rollback stays consumer-owned. Before diagrams migration lands, keep its existing generator and built baseline. If compatibility fails, leave the migration open and fix the adapter. A released regression uses a corrective version or a rollback to an earlier actual published version; never rewrite an already published version or replace it with a workspace path.
