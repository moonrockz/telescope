# Site tutorials

## Purpose

Let independent projects publish ordered tutorials through Telescope's standard site build, with useful static lessons and optional interactive workspaces.

## ADDED Requirements

### Requirement: Explicit tutorial configuration

The toolkit SHALL enable tutorials only through explicit configuration referencing a supported versioned TOML manifest. Existing sites without tutorial configuration MUST retain their behavior and MUST NOT load tutorial editor, formatter or execution assets.

#### Scenario: Existing consumer
- **WHEN** an existing version-one site configuration omits tutorials
- **THEN** it builds without tutorial pages, primary navigation entries or tutorial-specific browser assets

#### Scenario: Unsupported tutorial manifest
- **WHEN** a configured tutorial manifest has an unsupported schema version
- **THEN** the build names the manifest and supported versions and exits unsuccessfully before replacing completed output

### Requirement: TOML manifest authoring

The tutorial manifest SHALL use TOML tables and ordered arrays of tables, support comments and require an explicit schema version. Syntax errors and duplicate keys MUST identify the manifest and available line/column; schema errors MUST identify the offending field. Comments, whitespace and table-key order MUST NOT change routes, normalized inputs or generated bytes. Course and lesson array order MUST remain meaningful.

#### Scenario: Commented tutorial manifest
- **WHEN** a consumer supplies a valid TOML manifest with comments and tables for courses, lessons and providers
- **THEN** the build accepts it and preserves the declared course and lesson order
- **AND** adding comments or changing whitespace or table-key order produces the same normalized tutorial inputs and site output

#### Scenario: Malformed or duplicate configuration
- **WHEN** a manifest contains invalid TOML, a duplicate key or a field of the wrong type
- **THEN** the build reports the manifest with a syntax location or schema field path
- **AND** it fails before promoting output

### Requirement: Ordered courses and stable lesson identity

A tutorial manifest SHALL define courses with unique IDs, explicit ordered lesson lists, sections, titles and stable lesson slugs. Reordering a lesson MUST NOT change its route. Duplicate identities, unknown structural fields, missing prose and invalid lesson references MUST fail validation with the input location.

#### Scenario: Reorder a lesson
- **WHEN** a course changes its lesson order while retaining the course route and lesson slugs
- **THEN** the contents and previous/next links follow the new order
- **AND** existing lesson URLs still resolve

#### Scenario: Multiple courses
- **WHEN** two courses each contain a lesson with the same slug under different configured course routes
- **THEN** each lesson has a distinct stable URL and course navigation
- **AND** duplicate slugs within one course are rejected

### Requirement: Contained tutorial inputs

The build SHALL enforce declared-root containment, regular-file checks and output collision checks for tutorial manifests, prose, starting files, case overlays, source includes and browser assets. It MUST reject escaping paths and symlinks, invalid virtual file names and duplicate output routes before promotion.

#### Scenario: Escaping lesson resource
- **WHEN** a lesson file or include resolves outside its declared input root through traversal or a symlink
- **THEN** validation identifies the lesson and resource and the build fails
- **AND** the previous completed output remains available

#### Scenario: Tutorial collides with documentation
- **WHEN** a course index or lesson maps to a documentation or provider-owned route
- **THEN** the build reports both route owners and rejects the collision

### Requirement: Static lesson reading

Every lesson SHALL publish its prose, reference links, available starting-file text or downloads, source link and course navigation without browser execution. Static lessons MUST require no workspace, files, cases, editor or worker. Interactive lessons MUST identify that live checking needs scripting rather than show an indefinite busy state.

#### Scenario: JavaScript disabled
- **WHEN** a reader opens an interactive lesson without scripting
- **THEN** the lesson text, starting files, references, included examples and previous/next links remain usable
- **AND** no inactive editing or checking controls obscure that content

#### Scenario: Prose-only lesson
- **WHEN** a static lesson contains prose and tested source includes without starting files or cases
- **THEN** it renders at the standard reading width and loads no tutorial editor or execution assets

### Requirement: Tutorial navigation and search

Enabled courses SHALL appear in configured primary navigation and expose a grouped course contents page, current-lesson indication and previous/next links. Published lesson prose and included example text SHALL enter the active tree's search index. Private case data and saved reader edits MUST NOT enter that index.

#### Scenario: Find a lesson in an older version
- **WHEN** a reader searches for lesson prose inside a supplied older version tree
- **THEN** the result links to that tree's lesson and marks its course when opened
- **AND** other-version results, case expectations and reader edits are absent

### Requirement: Deployment-relative tutorial links

Tutorial page, asset, download and rewritten authored links SHALL resolve within the configured deployment base and supplied version tree. Repository-relative links to configured lesson prose MUST resolve to its published lesson route. External references MUST use safe web URL schemes without a Smithy-specific domain restriction.

#### Scenario: Project path and archived tree
- **WHEN** the same course builds under `/` and `/project/v/1/`
- **THEN** contents, lessons, includes, workers and downloads resolve beneath the respective base
- **AND** links between lesson source files and ordinary documentation resolve to published pages

#### Scenario: Unrelated project's reference
- **WHEN** a lesson links to its own documentation or an HTTPS reference outside smithy.io
- **THEN** the reference is retained and usable
- **AND** a script-scheme reference is rejected with its source location
